# 变更安全评估（Change Safety Assessment）

通用于**任何业务系统**的功能修改/新增安全评估。核心信念：**安全性由分级判定得出，不是感觉**。

## 判定模型（三层）

### L0 硬底线 —— 缺一即不安全（红线，不存在扣分制）

| 维度 | 评估变更时要检查的具体问题 |
|---|---|
| **① 一致性**（不产生脏数据） | 新写入字段有无合法来源？外键/引用完整性是否破坏？删除是否级联清理？有无唯一约束冲突？非法值能否入库（有无校验）？ |
| **② 时机合法性**（状态机/时间窗口） | 变更是否破坏现有状态流转？新增/修改的接口在错误状态/时间点能否被调用（有无状态校验）？**前端挡了、服务端挡了吗**（只靠前端不算数）？ |
| **③ 原子性**（全成或全败） | 多表更新是否在同一事务？失败路径是否全部回滚？有无"部分成功"残留中间态？无事务时有无补偿机制？ |

### L1 场景必检 —— 按操作属性对号入座，命中必检、未命中豁免

| 维度 | 命中条件 | 检查问题 |
|---|---|---|
| **④ 幂等性** | 操作可重复触发（接口重试/定时任务/多端重复提交） | 重复执行结果是否一致？全量重建（幂等）vs 增量叠加（不幂等）？ |
| **⑤ 并发安全** | 多人/多进程同时写同一资源 | 有无锁/版本号/唯一约束？还是 last-write-wins 静默覆盖？ |
| **⑥ 可恢复性** | 数据不可重建/高价值（评分/订单/资金/用户数据） | 删除覆盖前有备份吗？有审计（who/when/what）吗？出错后能否回滚？ |

### L2 增强项 —— 记录不判死

| 维度 | 检查问题 |
|---|---|
| **⑦ 可观测性** | 失败是否可感知？空结果/缺数据是显式报错还是**静默空**（最危险）？有无日志？ |
| **⑧ 性能** | 复杂度随数据量是 O(1) 还是 O(n)？锁粒度？全量重建/全表扫描在量大时如何？ |

## 判定规则（核心）

```
L0 三底线任一不过      → ❌ 不安全（禁止合入/上线），直接给修复清单
L0 全过 + L1 命中项全过 → ✅ 安全
L0 全过 + L1 命中项缺失 → ❌ 不安全（该项必检）
L0 全过 + L1 未命中    → ✅ 基础安全（L2 缺失仅记录，不判死刑）
```

**关键原则**：
- L0 是红线：L2 做得再好也补不了 L0 的缺。
- "满足几条算安全"没有固定数字：**3 条硬底线 + 命中场景的必检项全过**才算安全。
- 若结论为"条件安全"（如"窗口内安全、窗口失控不安全"），必须写清成立前提。

## 流程（5 步）

```
① 收集变更上下文
   改了什么？涉及哪些数据表/接口/状态流转？数据从哪来、写到哪、谁在读？
   → 用 trace_callers / find_references / file_dependencies 追数据流，别只看改动文件本身

② 识别变更类型
   纯读 / 写操作 / 状态流转 / 删除数据 / 配置变更 / 定时异步
   → 决定 L1 命中哪些维度（④/⑤/⑥）

③ 逐层评估 L0 → L1 → L2
   L0 三底线全过才继续；任一不过 → 直接判"不安全"，不再往下

④ 按判定规则出结论

⑤ 输出报告
   每个维度必须带证据（文件:行号）和可执行的修复建议
```

## 输出报告模板

```markdown
# 变更安全评估报告
## 变更概述
  功能：xxx；涉及接口/表/状态：xxx；数据流：xxx
## 最终结论
  ✅ 安全 / ❌ 不安全 / ⚠️ 条件安全（满足 xxx 后）
## L0 硬底线
  ① 一致性：通过/不通过 —— 证据（文件:行号）—— 建议
  ② 时机合法性：通过/不通过 —— 证据 —— 建议
  ③ 原子性：通过/不通过 —— 证据 —— 建议
## L1 场景必检（标注命中/未命中）
  ④ 幂等性：命中/未命中 —— 结论
  ⑤ 并发安全：命中/未命中 —— 结论
  ⑥ 可恢复性：命中/未命中 —— 结论
## L2 增强项（记录不判死）
  ⑦ 可观测性：静默空风险？有无日志？
  ⑧ 性能：复杂度？
## 修复清单（按优先级排序）
```

## 理论出处（供追问时引用）

- ① 一致性 / ③ 原子性 → ACID（Haerder & Reuter 1983；数据库教材）
- ② 时机合法性 → 有限状态机（FSM）；DDD 状态建模（Eric Evans）
- ④ 幂等性 → HTTP 方法语义（RFC 9110）；Stripe idempotency-key 实践；Kleppmann《Designing Data-Intensive Applications》
- ⑤ 并发安全 → 数据库并发控制：两阶段锁、MVCC、乐观并发（OCC）
- ⑥ 可恢复性 → RPO/RTO（ISO 22301）；审计要求（SOX / PCI-DSS）
- ⑦ 可观测性 → fail-fast vs fail-silent；Google《Site Reliability Engineering》
- ⑧ 性能 → 算法复杂度（CLRS）
- 上层元框架：CIA 三元组（完整性≈①④，可用性≈⑥⑧）、ACID、DDIA 可靠性定义、Design by Contract 前置条件（Bertrand Meyer）

## 执行纪律

- 每个判定必须给证据（文件:行号），禁止"感觉安全"式结论。
- 服务端必须与前端同强度校验——只靠前端禁用不算安全。
- 识别"静默空"（空表/空列表当正常返回）比识别脏数据更重要，它最隐蔽。
- 报告要诚实：L0 不满足就说不满足，不为了好交代而放水。
